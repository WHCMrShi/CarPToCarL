## 1. 音乐进度和播放状态

### 证据与原因

切歌时有 `0x5001 NowPlayingUpdate`，如 16:39:01 的 Call You Tonight、16:43:10 的海市蜃楼。17:25:08 暂停、17:25:17 恢复时，MediaSession 也能检测到状态。

但 `SessionController.kt:339` 的 `pushNowPlayingAll()` 仅以 `title|artist` 去重，相同曲目直接返回。进度变化、暂停/恢复、seek 均不能可靠触发车机更新。`buildNowPlaying()` 虽调用 `displayPositionAt()` 计算进度，结果仍需实际发送。

Wi-Fi `VirtualIap2Link.kt:688` 在订阅到达时回复一次，之后依赖宿主主动推送；没有持续推进位置的完整更新机制。不能假设仪表一定自行插值。

本地 blame 显示该去重逻辑在较早历史边界已存在；尚不能确认用户观察到的回归由最新哪个 release 引入，不应直接归责于近期 PCM 或视频优化。

### 修改建议和验证

- 分离曲目信息去重与状态/位置更新；播放中低频更新进度，暂停、恢复和 seek 立即更新。
- 按链路及订阅状态管理更新生命周期，断链后停止，重连后重推。
- `MediaListenerService.kt:185` 当前读取 `state.position`，却将锚点设为读取时刻；应核对 `PlaybackState.lastPositionUpdateTime`，避免把旧位置反复作为新采样。
- 回归：同曲播放至少一分钟、暂停/恢复、前后 seek、切歌、同歌名不同专辑、重连后仍在同曲。检查实际发送的位置与状态，而非只检查日志中的歌名。

## 2. 专辑名称和封面

`SessionController.kt:376` 对 MediaSession 数据源写死 `album = null`；`MediaListenerService.kt:177` 的 NowPlaying 构造也未采集专辑字段。CarLife 备用数据源虽有 album，但主源有效时优先使用主源，所以不能指望备用源补齐。

封面提取已有 `artFor()`，但 `iap2/Iap2NowPlaying.kt:19` 的数据模型及编码器没有封面字段或相应传输实现。在手机 UI 可见封面并不代表已发送给车机。

建议先增加专辑名的采集、模型和合并；封面单独确认 Q4 支持的请求/传输方式、格式、大小和缓存策略，不直接把图片字节加入现有文字参数。测试应覆盖封面晚到、切歌后旧封面清除、同名歌曲。

### 源码疑点和边界

- `mib3/Mib3ControlLink.kt:133` 只绑定蓝牙 `Iap2SenderSession`。Wi-Fi `VirtualIap2Link` 未接入同一套 EA 状态/数据处理；需核实这台 Q4 实际要求使用的通道，不能直接断言应改为 Wi-Fi。
- EA02 应用启动请求被忽略是重要线索，但不是“处理它即可修好”的证据。
- `Iap2SenderSession.kt:760` 明示 EA 数据以裸字节塞进 EA04 是推断形式。本轮没走到数据发送阶段，无法验证该假设。
- `handleEaStatus()` 保存原始状态，面板以任意非空引用的 EA03 作为 READY，未核对成功状态和所选协议。这是尚未触发的潜在问题。
- EA00 只补发一次；Wi-Fi 会话重建后没有与新就绪阶段绑定的完整重试策略。应先验证时序，不建议无限重试。

### 建议

先补齐每条链路的身份、EA00 参数、EA02 参数、EA03 状态与协议/会话关联，再核对数据承载和只读请求。保护所有车辆写操作，先验证只读往返。

保留 EA03 前禁止抢发数据的保护。`docs/audi-mib3-ea-tunnel-20261104.md` 中其他奥迪样本曾在未建会话时发 EA04 后停止 ACK；本轮面板操作未再触发那种故障。旧文档中“改完应当就绪”的推断不能代替本轮实车证据。

## 4. 方向盘语音键

16:48:24.844、16:48:32.304 两次仅出现 `requestSiri Prewarm`，随后有 changeModes；没有 ButtonDown/ButtonUp，也没有 VR_START 发送记录。

`carlife/VoiceKeyRouter.kt:94` 对 Prewarm 仅记日志；只有按下事件才发送 CarLife `0x68008 / VR_START`。所以本轮实际事件不会启动 CarLife 语音。

`SessionController.kt:3745` 对 changeModes 统一回答接管资源；`airplay/AirPlayClient.kt:703` 的 assertModes 使用固定 appStates / speechMode 与主屏、主音频声明。应检查它是否影响后续语音交互，目前只能作为疑点。

当前目标是 CarLife 内部语音入口，没有调用 OPPO 系统语音助手的路径。后续需先明确需求是 CarLife 语音还是系统助手。

建议完整记录请求参数及响应模式，测试短按、长按、语音页面入口；确认握手后再决定是否针对该车机提供 Prewarm 超时兜底。不能把所有 Prewarm 无条件映射为启动，避免误唤醒、重复启动和错误音频资源占用。

## 5. CarPlay 断开后 CarLife 保持连接

`SessionController.kt:1397` 手动 disconnect 经 `retireSession()` 清理投屏；`retireSession():1440` 使用 `CarLifeHijack.detach()`。`carlife/CarLifeHijack.kt:594` 明确只摘视频发送器、保留 CarLife 连接和缓存。真正停止连接、音频接收器、线程与缓存的是 `stop():601`。

这是为跨配对/短暂重连保留引擎而设计，但缺少用户最终断开的完整清理区分。日志结束时仍在推流，没有用户最后断开的证据，因此本轮不能定位最后操作的精确调用路径。

建议区分临时退役与最终退出：重连保留；手动结束完整停止；长期失联延迟清理。不要将所有 retireSession 改为 stop，因为配对起步也调用它。验证应覆盖主动断开、车机关闭、Wi-Fi 短断、自恢复和再次手动连接，并观察 CarLife 状态及后台资源。
