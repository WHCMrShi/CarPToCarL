# 2026-11-13：预期蓝牙交接后的补连判定

开发基线`9bc1a6b`。用户要求修复关键连接逻辑，完成后先自审再构建；同时缩短Wi-Fi重连提示、统一顶部卡片和Live Updates短文本。本轮不研究最初Wi-Fi丢失及媒体抖动。用户倾向车机启动初始化造成初次丢网，并反馈媒体抖动明显受手机操作/性能影响；这是用户判断与体验反馈，尚非新的系统根因证据。

## 依据和改动

[下午实车证据](analysis.md)已经记录：15:23:47.604命令200，随后BT iAP2关闭，Wi-Fi控制与CarLife持续；原逻辑却补连5轮10次。原`Iap2BluetoothClient`只区分本地主动拆链与非主动断链，没有识别命令接受后的交接。这是本次改动依据，不增加猜测性的重试阈值或等待。

`AirPlayClient`将命令是否获得200记在当前BluetoothDisableSession内。读取和发布都校验该控制连接的generation、资源scope及SETUP身份；close/替换SETUP后旧结果不能作为新会话的接受状态。未发送、等待应答、422、超时或IO错误均不成为“已接受”。accepted仍仅表示命令接受，不声称所有profile/ACL已经断开。

`SessionController`在发送前捕获当时活跃的BT owner，并登记一个只读取当前状态的交接条件：connection/setup工作票据仍有效、未取消、仍为同一AirPlayClient、该会话命令已接受、Wi-Fi iAP2控制会话仍就绪。发送前登记不等于提前暂停恢复；必须等200才能成立。没有新增CarLife启动门禁或改变命令发送时机。

`BtLinkRecovery`将原恢复目标/时刻与具体BT owner关联。预期交接成立时返回“暂停恢复”，不发起补连；关闭回调先到而应答后到时，已有恢复任务也会在收到200后停止提供拨号目标。拨号/释放协调继续通过原BtProfileOperation的动态有效性检查，尚未执行的后续动作随之失效；已经提交的平台调用不能宣称可撤回。

| 情况 | 行为 |
| --- | --- |
| 本会话200、同一BT owner、Wi-Fi控制仍就绪 | 暂停该owner的补连 |
| 未发送、等待应答、拒绝、超时、IO错误 | 保留原恢复行为 |
| 已接受，但Wi-Fi控制不再就绪、client关闭、connection/setup票据失效 | 不再按预期交接暂停；若会话仍活跃且原恢复窗口未到期，可继续原恢复 |
| 新BT owner或换车接续 | 旧owner的接受结果不覆盖新owner |
| CarPlay会话结束/用户停止 | sessionActive清除时重置恢复及交接登记 |

原180秒恢复截止时间不延长、不重置，原入站接续、出站拨号、先直连再释放、退避参数不变。Wi-Fi失效后的正常会话重建仍由已有流程负责，本次不引入另一套恢复。BT-C新增预期交接日志，沿既有诊断归档收录。

## 完成后、构建前自审

逐一检查了实际调用链、异步发布、工作票据、owner替换及拨号前的有效性检查。发现并修正两项有确定性代码交错依据的问题：

1. 不能先读取恢复目标，再另读“是否预期交接”来解释null。200或Wi-Fi关闭可能插在两次读取之间，把暂停误当成超时并清掉任务。改为单次Decision同时返回目标和原因，测试中在返回后改变Wi-Fi状态，确认旧决定不会被重新解释。
2. 超时决定形成后，新BT owner可能已经接手并登记新丢失。旧决定的清理必须带原owner；新增确定性交错测试，确认旧清理不能删掉新目标。退役与真正超过180秒分开输出，避免错误的超时日志。

其他核查：状态回调不在恢复对象monitor内执行，避免该锁跨入AirPlay/work状态读取；命令迟到200不能发布到替换后的SETUP；暂停时保留原截止时间，避免失效后获得额外180秒；每次新的owner与工作票据均隔离。未发现需要扩大到Wi-Fi初始化、媒体调度或系统设置的修改依据。

## UI文案

- 重连提示：`车机热点已断开，正在重新连接`；无可用凭据时为`车机热点已断开，请重新连接`。不展示SSID及内部重绑说明；详细技术日志保留。
- 顶部连接标题使用`未连接 / 连接中 / 已连接`。连接中/已连接与Live Updates读取相同字符串资源，防止两处措辞漂移；本轮不改变它们原有状态判定及通知权限行为。
