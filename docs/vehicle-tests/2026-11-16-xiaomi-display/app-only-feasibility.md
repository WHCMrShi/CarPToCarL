# 只修改我方应用：首次编码前的尺寸与直通配置可行性

日期：2026-11-16；分析基线 `47824f707fed`。用户限定本轮只分析、不改代码，不能修改 CarWith 或小米独立引擎。本文只记录候选方案及边界，不表示已实施或实车验证。主包为已核对的 CarWith 4.0.9-20260629；独立引擎仍是公开参考包 8.8.4，未与车友安装版对齐。制品身份见 [引擎尺寸链](engine-size-chain.md)。

后续用户已授权实施其中的统一首轮入口与65617响应，见[实现、自审及OPPO安装记录](first-init-gate-fix.md)，业务提交ff2034e。下文保留分析阶段的判断，不据后续安装宣称本方案已在车机验证。

## 结论

**有可实施的我方握手修复方向：将首条98311收敛到统一入口，在同一控制连接上先发送98386、再发送不可变快照中的1412×654，并及时响应65617。** 它可以排除我方多线程抢跑、版本未匹配就初始化、没有回应手机特征请求等问题。参考引擎正常初始化路径具有同线程队列顺序依据，比继续猜ACK或延长等待更强。

但不保证这就修好车友样本：其日志已经多次显示98386先于正确尺寸的98311约2秒。只有在目标引擎是全新编码状态、特征执行成功且厂商没有再次覆盖的前提下，才可期待精确输出。已初始化720p、特征执行异常、厂商持久档位覆盖都不能靠同会话多发98311排除。不能把“排除我方时序缺口”写成“已证实就是本次根因”。

## 参考引擎为什么允许以发送顺序建立先后关系

新增核对以下调用链，并用dexdump交叉确认核心调用（不执行APK）：

1. `CarLifeApplication.syncOnCreateTask` 的主进程初始化调用 `CarlifeConnectInitUtils.initConnectModule`；后者先初始化 FeatureConfigManager，再初始化视频模块。
2. FeatureConfigManager 构造消息处理器时调用 MsgBaseHandler 默认构造；该构造取当前Looper，无Looper才回落主Looper。因此**正常由Application主线程首次构造时**，该特征Handler绑定主线程。不能笼统说这个类无论如何都显式绑定主线程。
3. VideoMsgHandler 明确在主线程创建 `VideoHandler(Looper.getMainLooper())`。
4. 控制 socket 的单条 `ConnectSocket.ReadThread` 依次完整读报文，然后调用 `MsgHandlerCenter.dispatchMessage`；该分发把消息以0延迟交给相应Handler。98386执行excute同步赋值useVehicleResolution；98311在视频Handler内读取此标志并调用initMediaCodec50。

据此，在两Handler均已注册、走上述初始化路径、同一有效连接、没有中途uninit/另一发送者/特征执行异常时，同一控制流先98386后98311，主队列应先执行特征处理，后创建编码器。没有必要依赖麦克风事件，队列拥堵本身也不会把同队列的后续普通消息变成先执行。

这不是远程应用成功的ACK：FeatureConfigManager.excute有覆盖整段循环的异常捕获；中途异常可能跳过后面的直通键。默认构造的首次线程、实际安装版本以及断连清理插入也仍是条件。没有在协议3.0普通路径发现专门证明直通赋值已完成的回包。65544只能说明编码初始化回报，最终仍要看SPS。

## 我方当前的可修复缺口

以下符号以本次基线为准，不混作bcef70f源码行号：

| 入口 | 当前行为 | 首次创建前的风险 |
| --- | --- | --- |
| MD_INFO握手线程 | 等版本最多3秒，配置后本地2秒再初始化 | 版本等待超时后仍可继续，且只约束本线程 |
| videoSupervisor → reopenVideo → restartEncoding | 重连分支位于versionMatched检查之前，300ms后配置、再600ms初始化 | 能早于正常握手线程，且没有版本匹配门禁 |
| videoSupervisor → resendEncInit | 无帧重试仅等待300ms即发98311 | 检查版本但不检查首轮特征已发送 |
| requestVideoReinit → restartEncoding | 与视频重连使用相同路径 | 可能在首轮尚未完成时进入 |
| VIDEO_ENC_DONE(65551) | 直接sendEncoderInit | 未检查首轮特征/版本阶段 |
| setRequestedResolution | orderedInit且首条未发送时只更新尺寸 | 这一入口已有让位规则，但不能约束其他入口 |
| requestSourceKeyFrame | orderedInit且首条未发时有界等待 | 这一入口已有首轮保护 |
| sendEncoderInit(force) | 集中打包发送、5秒去重 | 没有首轮阶段门禁；force会绕过去重，无法维护全局首轮顺序 |

另一个独立缺口：`MD_FEATURE_CONFIG=65617`只定义了常量，没有handleMessage分支，cmdReader也不拦截处理。此前纠错文档所称“既有入口”不准确，应改为“已有常量，尚未接入处理”。车友这份日志未找到65617记录，不能说该样本已经观察到请求被忽略。

参考引擎在处理HU_STATISTICS后调用FeatureConfigManager.request，向HU发65617，并启动1000ms定时器；超时派发内部1008并标记成功，**不等于收到了直通配置**。我方在65538时发送HU_STATISTICS，却只在MD_INFO线程主动发配置。相对MD_INFO定时发送不是响应65617。应及时响应真实请求，并保留兼容没有该请求的引擎的有界主动路径。

## 建议的我方方案，按优先级实施

### 第一优先：唯一的首轮推进器

不是再给MD_INFO线程增加等待，而是让**所有98311发送请求**都经过一个会话所属的推进器：

1. 会话创建时就拥有正确画布。Q4分支目前已用 `CarCanvasMemory.DEFAULT=1412×654` 给HU构造参数，日志也确认首条申请正确，本样本无需等待CarPlay /info才能知道尺寸。
2. 未版本匹配、尚未具备手机设备信息/特征请求所表明的握手进展时，首条98311不能发送；恢复/关键帧/重复MD_INFO仅登记需求，不另开线程抢首轮。版本等待超时结束本轮或报告握手未完成，不放行编码。
3. 由同一个发送序列在当前控制连接先写98386（直通=1），写成功后再写唯一首条98311。宽高/安全区/适配参数作为一次不可变快照读取，避免两次可变字段读取或迟到更新混入。两次发送间不得被其他首轮任务抢占。
4. 收到65617立即排入同一序列响应98386；没有请求时允许在握手已就绪后主动发送，不能无限等待65617。把“配置已发送”与“引擎已应用”分开命名。接收线程不sleep等待后续事件，以免阻塞自身读包。
5. 是否暂时保留2秒本地预算可独立验证；逻辑正确性应来自先后关系和全入口门禁，不来自这个时间值。重复特征请求不能无限刷新预算；旧会话延迟任务不能向新连接写数据。

这保留CarLife先起的预连接收益。CarPlay先连时，应在启动HU前带入已验证画布；当前worker在hu.start成功后才回放requestedW/H，通用车型路径不能只依靠“握手线程通常还会等2秒”保证回放赶得上首条。对本样本两处值均为1412×654，未证明此回放边界造成降档。

可考虑把DISABLE_RESOLUTION_OPTION放在特征列表前部，减少其他键副作用异常阻断它的机会；这是异常隔离实验，不能代替统一门禁。目前没有证据表明CONNECT_TYPE等处理确实抛异常，不建议仅凭推测删配置。

### 第二优先：仅在确有旧初始化嫌疑时做完整会话重建

参考ConnectSocket读错误会调用ConnectClient.setIsConnected(false)；当其内部原状态为已连接时派发1002。CarlifeConnectHsgHandler处理1002会清mInited和直通标志。由此，我方关闭完整CarLife连接后重新握手，存在让目标回到首次编码状态的正常协议路径，无须改厂商包。

限制必须保留：只重连视频口不等于全局重建；内部尚未标记已连接时，setIsConnected(false)未必派发1002；读线程收尾和异步清理也不能靠我方running=false视为完成。不得用某个未经验证的固定毫秒数宣称旧编码器已经清理。

如后续实现，应在首轮结果不符时最多进行明确限次的完整会话重建，旧任务全部退役，重新走第一优先的顺序。通过新的版本/设备信息交换和首个输出验证，而不是把新socket本身当作清理确认。已有画面/音频的源会被中断，不能默默无限重连，也不能借此取消既有稳定出帧路径的恢复边界。此项可行性低于统一首轮门禁，尚需设备A/B。

### 不优先走的捷径

- 延长固定延时、根据65570或其他邻近事件猜ACK：缺乏完成语义。
- 只发98315、重复98311或force=true：参考实现不提供预期的重建保证。
- 改成协议3.2/4.0：会进入新的鉴权/加密及新车机分支，范围远超尺寸排序；当前3.0已支持直通键。
- 换channel以躲持久档位：还会回落全局档位，且改变身份/授权/兼容分支，没有确定性收益。
- 改needAdapterScreen或安全区为“精确尺寸开关”：本次所见CarWith保存尺寸覆盖并不以这些值为绕过条件，且会引入布局/触摸副作用。
- 以我方转码作为首选：不能修复源虚拟屏已经裁掉的内容；当前目标是先让源输出正确。

## 能证明什么，以及怎样验收

第一优先可用本机确定性交错测试证明：所有入口都不能绕过首轮门禁；版本超时不发初始化；65617有/无/重复都不会死锁；写失败不推进；首条快照是1412×654；旧会话任务不能写新连接。它只能验证我方，不验证厂商已应用。

设备实验保持真实通告1412×654，分别覆盖CarLife先起与CarPlay先连，区分全新完整会话和仅本应用重连。记录首条98386/98311发送来源、会话代次、申请快照、65617是否出现、65544以及首次SPS。**首次SPS必须为可见1412×654，并由照片确认内容完整**；回包尺寸相等或写成功不足以验收。

若严格顺序和完整新会话仍只输出720p，才能说明这一我方方案不足，继续区分目标引擎版本与厂商持久覆盖；不要增加重试直到偶然成功。现有日志已正确申请1412×654且先写配置，使本方案具有工程依据但对样本的修复把握有限，不能承诺只改握手一定解决。
