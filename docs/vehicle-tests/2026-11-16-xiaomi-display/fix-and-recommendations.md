# 65570 纠错与 CarWith 分辨率修复建议

日期：2026-11-16。依据 [独立引擎尺寸链](engine-size-chain.md) 与 [CarWith 主包尺寸链](source-size-chain.md)。本次用户明确授权修复 65570，导航距离单位测试另行提交；以下分辨率策略仅为建议，没有实施厂商补丁或新的重启/改档策略。

协议修复提交 `67a5e82`，导航测试提交 `5fe944a`；本文件引用修复后的符号与提交，不混用基线 bcef70f 的行号。

## 本次落地的协议纠错

`CarLifeProtocol.MD_MIC_RECORD_WAKEUP_START=65570` 替代错误的 `MD_FEATURE_CONFIG_DONE`，移除 `featureConfigAcked` 及其所有赋值。收到该事件只限次记录麦克风唤醒，不响应、不启动录音、不改变编码初始化状态。65617 仍是手机请求特征配置的既有入口，没有改成另一种 ACK。

有序首轮与稳定后补发两条原先依赖错误 ACK 的路径，改为 98386 后固定 2000ms 本地间隔；沿用旧等待上限，50ms 分段检查运行状态，停止或中断时退出。任何 65570 都不能缩短或延长它；没有事件也能继续发 98311。日志明确写明没有协议 ACK、未确认引擎应用。其余已有的探测、看门狗、热更新时序保持原策略，只纠正相关注释中的确认/重建断言。

**行为代价**：旧实现若约 0.7s 收到麦克风事件，会提前结束等待；现在两条被修正路径都等满 2s，比旧提前放行情况增加约 1.3s。此间隔只是保守保留的本地预算，不是引擎处理屏障，也不是 CarWith 分辨率修复。没有延长旧最大等待，没有新增无限等待。

原“二次初始化能强制重建”的日志同步改正：`force=true` 只绕过我方发送去重，小米参考引擎在 mInited=true 时根本不解析新尺寸。本次保留其现有默认行为，未把尚未实车验证的取消补发混入纠错。

新增 `FeatureDispatchTest` 通过真实消息路由和有序初始化输出检查：65570 身份及无响应、无该事件也可完成配置后初始化、事件不能提前放行、停止与中断取消等待。另修正导航组合测试两处旧的“500米”预期为当前“500m”；现有 NavigationStateTest 已覆盖 1000 米显示为 1km，不改单位业务逻辑。

## 分辨率修复的建议顺序

我方普通 HU 应用可以改发送顺序和申请值，却不能仅靠 98311 改写 CarWith 私有档位或强制其内部编码器重建。下列厂商/引擎修复点需要维护方修改对应实现，或另行经过授权的验证环境；本次没有引入 Hook，也没有修改或重签厂商 APK。

### 1. 先解决首次创建与已初始化状态

目标不是多发几次 98311，而是让实际首次创建编码器时读到正确尺寸和直通状态。

- 我方已在首轮发送 `DISABLE_RESOLUTION_OPTION=1`；本次不再用麦克风事件证明它生效。后续若改握手，应依据实际引擎处理状态或可验证的生命周期推进，不另猜一个 ACK，也不把固定延时写成成功判据。
- 参考引擎修复点在 `VideoMsgHandler.VideoHandler.handleMessage(98311)`：已初始化时比较新请求和当前配置。相同则回当前状态；不同则走受控的停止/释放/按新尺寸创建编码器与 Surface、重新绑定显示的流程，成功后再回确认。不能只清 mInited 而不释放旧资源，不能只改回包尺寸。
- 无法改引擎时，验证应使用真正结束 CarWith/独立引擎会话后的首次连接，确认目标全局清理执行；我方 socket 重连或重开应用不能替代。不要以 98315 强制重建，参考 APK 中 resetVideoTrans 为空。

对本样本，65544 和 SPS 同为 1280×720，优先排除这里以及首次 useVehicleResolution=false 的标准分档。引擎版本 8.8.4 是公开参考包，未证实车友实际安装版，以上方法名和行为须按实际包复核。

### 2. 修正 CarWith 保存分辨率覆盖的优先级

已核对的 CarWith 4.0.9-20260629 在 `com.xiaomi.ucar.carlife.c.i(...)` 处理 `carlife_encode_format` 时，优先采用 `<channel>_current_resolution_key`，继而全局 `car__current_resolution_key`，覆盖本次 real_width/real_height。

建议厂商在此边界落实直通语义：当请求明确要求精确分辨率（引擎传入 res_accuracy）且本次 real_* 合法时，以本次尺寸为优先，不再让旧的当前档位无条件覆盖；普通非精确模式仍可使用用户选档。不要直接把 width/height 原始申请套到所有模式，应先确认 real_* 是本轮选择结果及直通标志。保存值应带显示目标/有效模式的适用条件，不能跨目标继承旧 720p。

本机验证可先查看 CarWith 是否提供清除/重选分辨率的入口，对照设置前后首次连接；不能在未备份、未确认存储键语义时全量清应用数据。冷重启并不会清掉持久档位。当前没有这台手机的保存值，不能断言“清缓存一定修复”，更不能要求车友仅靠换 CarPlay 摆放排除该覆盖。

### 3. 统一最终编码格式与虚拟屏尺寸

参考引擎 `MediaFormatUtils.setVendorEncoderParams` 会采用厂商返回格式；`Recorder.configMediaFormat` 却只在 useVehicleResolution=false 时把最终宽高回写到内部尺寸。应在最终格式确定后，对所有模式统一校验并同步实际编码宽高，再创建输入 Surface，保证 65544、mMediaWidth/Height、mWidthEnc/HeightEnc、CastConfig 及包装渲染目标以同一最终有效尺寸为基础。需保留编码器实际尺寸限制及显式失败处理，不能伪造 1412×654 的确认来掩盖 720p。

厂商确实无法编码精确尺寸时，应明确协商替代尺寸和适配方式，并使虚拟显示、渲染目标、码流及触摸映射一致；不要让内部仍报 1412×654、MediaCodec 却配置为 1280×720。本轮没有证据证明硬件不支持该尺寸，因此不优先加转码、缩放或硬编码 720p。

按一次会话关联以下语义字段即可，不需要公开身份或整包负载：

| 首次处理 98311 | mInited、useVehicleResolution、收到的 1412×654 |
| 首次选档后 | mMediaWidth/Height |
| 厂商回调 | real_*、res_accuracy、保存档位是否命中、返回 width/height |
