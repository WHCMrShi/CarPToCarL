# 2026-11-13：预连接收益与复用撤销请求的必要性

只读评估基线 `0d33a6e`；先评估收益，再审查所有权。没有改变代码、配置、手机设置或权限，未执行单测/构建，没有新增实车实验。以下源码以函数名和提交定位，不使用当前行号冒充约定的 `bcef70f` 行号。

## 收益应拆成三件事

| 功能 | 有依据的用途 | 本轮判断 |
| --- | --- | --- |
| 记住并固定使用已成功的凭据 | 用户既定策略；有本轮目标邀请时，可减少对蓝牙重新下发凭据的依赖 | 不建议随预连接一起删除 |
| 已连车机Wi-Fi时提前复用、广播和发现 | 提前完成本进程绑定、使服务落到目标网络，并准备以当前邀请接续 | 早间确实提前完成；未证明最终连接提速多少 |
| 尚未连上热点时主动发起specifier | 将热点关联/DHCP等准备与蓝牙并行；为凭据迟到但已有邀请的情况准备网络 | 有合理收益机制，但现有样本未量化端到端净收益；午间直接参与了后续关联切换链 |

最初的真实问题见[11月9日交接](../2026-11-09-night-handover/handover.md)：23:05:55.345已有车机ctrl邀请，但入站蓝牙没有取得AP凭据；出站到23:06:14.206才拿到凭据。邀请到凭据间隔18.861秒，说明“缺凭据”可以成为前置阻塞。**这不是预连接已省下18.861秒的证明**：该样本是功能引入前，且不知道若有缓存，Wi-Fi和车机端口会何时就绪。

`1035322` 的目标是缓存已验证凭据、提前入网、由本轮匹配目标的邀请授权缓存端点接续，而非凭旧密码直接连接历史端点。当前 `cachedEndpoint` 不恢复旧IP、Network、socket或邀请；`startRememberedWifi` 和 `onCtrlInvite` 仍要求当前工作、目标和邀请证据。记忆不能解决车机7000未开放、蓝牙生命周期错误或CarLife源晚到；不能把这些阶段的等待全部算作可由预连接消除。

早间网络绑定比新凭据早约25.240秒，但配对仍发生在凭据到达后1.226秒；准备提前量不等于节省25秒。该次复用阶段只报告40ms，也不能将40ms当作移除预连接后的确定损失：预广播是否促使车机发现/邀请提前、异步调度及发现耗时，都没有无预连接的同条件样本。

午间首次绑定比新凭据早9.820秒，预请求本身比凭据早约22.4秒开始，但提前得到的网络没有持续到正式配对。不能把12.646秒的请求耗时全算成收益，也不能算成额外损失；没有关闭预连接的反事实样本。实际额外关联切换已有系统历史支持，默认网络策略失效的最后一环仍未确认，见[生命周期核查](wifi-lifecycle-review.md)。

两轮配对都发生在本轮新凭据到达后，尚无这两份日志证明“仅靠记忆和邀请，在新凭据到达前完成CarPlay”。[11月11日样本](../2026-11-11-q4-171732/analysis.md)虽有Wi-Fi地址先到、绑定晚约10.278秒，但缺完整预入网诊断，不能拿这个间隔宣称预连接应省下多少。两个11月13日样本还分别带dirty和不同蓝牙时序，不是严格A/B。

评估结论：**保留凭据记忆有明确用途；提前复用已有Wi-Fi有可见准备效果；提前主动关联热点的净提速尚未证实。** 上轮提出暂停主动预连接是有依据的对照候选，不能直接升级为“已经证明应永久删除整个记忆功能”。

## 复用为何会撤销旧请求

这是当前资源模型的结果，不是Android要求复用必须断开旧请求。

| 历史节点 | 核对结果 |
| --- | --- |
| `764845d`（10月29日） | 新增 `bindCurrentWifiBlocking` 时入口已有 `release()`，使用单一callback保存网络请求 |
| `fdbbd98`（11月4日） | 新增 `adoptIfAlreadyConnected`，直接复用这个开头会 `release()` 的函数；其目的为避免再次specifier确认和重连等待 |
| `140a6aa`（11月8日） | 将兜底改为被动 `registerNetworkCallback`，以继续观察已选网络的丢失；改变监听方式没有拆开主动请求的所有权 |
| `562b24f`（11月9日H1） | 将原先显式release改为 `OwnedSlot.replace(..., disposeRequest)`；修复旧任务/取消/finally清理新请求的竞态，延续单槽替换即处置旧请求的行为 |

H1的必要性有[当时review记录](../2026-11-09-q4-review-fixes/repair-notes.md)和当前测试覆盖支持；不能因为本轮有拆链副作用就整项回退H1。更早的清理实现本来就存在，不能将“复用撤销旧请求”误称为H1才首次引入。

当前路径是 `adoptIfAlreadyConnected → bindCurrentWifiBlocking → callback.replace → disposeRequest → unregisterNetworkCallback`，然后才注册被动观察。主动请求和观察共享 `callback`、`bindingCurrent`、`boundNetwork`。替换时立即撤销旧回调的修改资格，顺便注销其Android请求并解绑进程，使旧事件无法污染新绑定；但也把仍可能维持物理关联的资源一起撤销。

这不是每次复用都会拆连接：`joinCarWifiOnce` 在相同SSID且 `usableNetwork` 非空时直接返回，早间40.552就是这个分支。午间旧Network失效，才进入会替换callback的复用流程。**旧Network不可用与旧主动请求已释放不是同一件事**，不能用前者直接代替后者的判断。

## 哪些清理必要，哪些不必要

[Android ConnectivityManager文档](https://developer.android.com/reference/android/net/ConnectivityManager)区分主动请求与观察注册；注销主动请求可能拆除仅为该请求建立的网络。它允许多个受管理的请求/观察注册，存在总量限制，但没有要求新增一个独立观察者之前先注销已有主动请求。当前 `startIdentityObservation` 就已经使用独立callback与主动请求共存，普通App权限可实现。

| 场景 | 所需行为 |
| --- | --- |
| 用户停止、所属连接终态、目标切换 | 退役所属请求及观察者，阻止迟到事件继续绑定；该清理保留 |
| 已明确取消/替换的请求，或系统已报告不可用 | 结束对应生命周期、清理其资源；旧清理不能触及后继所有者 |
| 原主动请求仍属于当前连接，只是要观察并核对同一目标网络 | 观察本身不构成撤销主动请求的理由；保留其注册不等于认定旧Network可用 |
| 被动探测结束或超时 | 清理该探测的观察者；不能仅因探测结束便取消另一个仍被当前连接需要的主动请求 |

**需要取消的是失去使用理由的请求，不是每次进入复用都取消。** 不建议简单删掉 `disposeRequest`：那会丢失旧callback引用、泄漏注册，且多个回调仍可能同时绑定/解绑。也不能简单改成“先绑定成功再注销旧请求”：若新观察者看到的正是旧主动请求维持的网络，注销后仍可能拆掉它；绑定成功不是请求生命周期已交接的证明。

可行设计方向是把“维持目标Wi-Fi的主动请求”“用于身份/能力核对的被动观察”“当前进程绑定”分别管理，同时保留唯一的绑定决策者、当前目标和工作代次校验。请求是否存在、Network是否可用、进程是否绑定分别记录，不能互相代替。这不需要隐藏API、ADB授权或修改系统蜂窝优先策略。

## 后续取舍与验证边界

1. 保留固定凭据存储和当前目标身份校验，不把它们与主动预连接一起删除。
2. 复用撤销请求的副作用有明确源码依据，应独立处理；即使关闭主动预连接，正常0x5703入网后再次复用仍可能遇到同类问题。
3. 若做预连接对照，建议收窄为：目标Wi-Fi尚未可用时不提前主动请求，保留已连接网络的有验证复用、凭据到达后的正常请求及邀请接续能力。不能直接删掉整个 `startRememberedWifi`，否则缓存端点/邀请接续也一起消失，实验不再只比较主动关联。
4. 未来实现需验证：新增/超时被动观察不注销活跃主动请求；旧回调/旧finally不解绑后继网络；终态清理没有遗漏；Network失效后不把旧对象当成功；重复凭据共享现有工作。现有 `WifiMemoryRecoveryTest` 主要覆盖调用等待和工作票据，`WorkOwnershipTest` 覆盖单槽归属，尚未覆盖主动请求与被动观察并存的资源生命周期。本轮只阅读测试，没有运行或新增测试。

以上是实现边界和实验建议，尚未实施。实车仍需分别验证CarLife先连接、CarPlay先准备连接，并比较连接耗时、Wi-Fi中途切换及整机联网；不要求车上连接ADB，不把新观察者注册成功或本地绑定成功当作实车修复成功。
