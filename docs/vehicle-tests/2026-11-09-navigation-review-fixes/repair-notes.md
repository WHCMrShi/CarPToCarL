## “128”到底限制什么

当前实现的范围为 0x80～0xFF，其中 0x80（十进制 128）用于空图，所以普通图片只分配 0x81～0xFF，共 127 个 ID。f2814f4 引入了“同一连接不把 ID 分配给不同图片”的保守策略：防止接收端按 ID 缓存而显示旧封面。分配计数在 newLink 才清零，并非每首歌或订阅重置时清零。

公开转载的 [Apple MFi Accessory Interface Specification R2](https://www.scribd.com/document/325596037/MFi-Accessory-Interface-Specification-for-Apple-Devices-R2) 第 25.3 节描述的是每方向最多 128 个**并行**传输；25.3.1 描述循环寻找 inactive ID，25.3.8/10/11 描述 Cancel/Success/Failure 后 ID 变为 inactive。这份历史规范并未规定一生只能传 128 次文件，不能用它证明 Q4 的现代 ID 缓存行为、范围或刷新保证。

因此，“连续播放 127 首歌就不更新封面”不准确：

- 修复前，切换导致的每次新 ID 分配都计数，A→B→A 也分配三次；连续同封面不重复分配；失败重试可能额外分配。第 128 次普通图片分配会退为空图，文字和音频仍继续，直至新链路重置预算。
- 修复后，成功的 A→B→A 只用两个 ID，第三次仍重传 A 的字节。导航重复箭头及反复切换音乐/导航不再必然耗尽预算。
- **本次没有取消不同内容的 127 次新 ID 分配上限。**127 张全新图片全部分配后，第 128 张全新图片仍退为空图；之前成功登记的图片仍可正常复用。失败/未完成图片也可能消耗未回收 ID，不能把预算严格等同于不同成功图片数。
- 若要彻底消除全新图片的累计上限，需要独立验证 Q4 在同一 ID 下更换字节是否刷新，而后实施 inactive ID 回收；不能只把计数器取模就宣称可靠。协议层允许回收与实车展示正确是两个证据层次。
