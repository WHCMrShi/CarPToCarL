## 实现

`SessionController` 在原激活阶段为当前 SETUP 登记延迟条件，保持原识别、认证、SETUP、RECORD 与音视频建立顺序。`AirPlayClient` 先立即检查，条件不足时由既有 `/feedback` 心跳重新检查，不增加轮询线程，不在媒体回调中进行网络操作。心跳可能受现有请求耗时影响，因此不承诺固定一秒内发送。

发送必须同时满足：本轮激活 RECORD 已接受；当前 Wi-Fi iAP2 控制就绪；连接与 SETUP 工作、AirPlayClient 及 VideoSender 仍属于本轮；当前 CarLife HU 活跃且已有近期真实非空视频帧。条件不足只记为延后，不消耗本轮的一次发送机会。

`CarLifeSourceEvidence` 为每个 HU 源分别记录帧证据。证据来自该 HU 的真实输入回调，不来自提示帧、视频发送器运行状态、累计帧数或缓存回放。源被接管前收到的真实帧可以保留，接管后仍需核对 HU、源身份、warm scope、投屏归属和发送器；沿用现有源活跃判定的 10 秒新鲜度（小于 10 秒）。源停止、替换、过期或投屏所有者变化后，已捕获的源凭据不再满足条件；退役后的迟到帧不能恢复该源的有效性。

后台发送将“已排队”和“已尝试”分开。取得 RTSP 写锁后，紧邻实际写请求再次核对当前工作、Wi-Fi iAP2 和原源凭据；排队期间源停止或换代，会放弃本次排队而保留后续条件就绪时的发送机会。真正准备提交命令时才消耗一次机会，并登记当时的蓝牙 owner。命令拒绝、超时或发送错误后仍不重试，不延长蓝牙原有恢复窗口或改变退避。

命令 200 后才允许原有预期蓝牙交接判定生效，且仍要求对应 owner、控制会话和工作归属有效。保持关闭先到、200 后到的兼容处理；旧 SETUP 的排队工作与迟到结果不能影响新 SETUP。

独立审查未发现新增锁循环或阻断性问题，并补充了“排队期间控制就绪失效”的直接回归。写锁内复核消除了等待写锁期间的陈旧条件，但不能撤回已经提交给 socket 的命令，也不承诺源或物理链路在复核后绝不变化。

## 两种顺序与边界

| 情况 | 修复后的动作 |
| --- | --- |
| CarPlay 先完成，CarLife 尚未启动 | 延后本应用的 `disableBluetooth`；继续等待真实源，不以提示帧满足条件 |
| 同一 CarPlay 会话中 CarLife 晚到 | 当前 HU 真实供帧后，下一次有效检查可发一次命令 |
| CarLife 先供帧，CarPlay 后建立 | 正常缓存起播；投屏接管及其余条件满足后可发一次命令 |
| 源先就绪、Wi-Fi iAP2 晚就绪 | 后续心跳重新检查，避免在原唯一调用点跳过后永久不发 |
| 取消、源/SETUP/发送器替换或排队时源失效 | 旧凭据不能发送；本轮有效的新源可在未尝试情况下重新满足条件 |
| 命令已真正尝试后失败 | 沿用一次尝试与原恢复机制，不新增命令重试 |
