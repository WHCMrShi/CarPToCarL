### 16 秒的来源、触发与收益判断

源码：`bt/Iap2BluetoothClient.kt` 的 `connectLoop`、`tryConnect`、`backoffMillis`、`sleepBackoff`。

1. 首轮保留已有配置文件先拨 …caff；失败后调用 `BtProfiles.disconnect`，再拨一次。两次均未建起出站 socket，才进入失败退避。泛化错误 `A Bluetooth Socket failure occurred` 不能精确证明 SDP 缺失、车机忙或特定 HFP 策略。
2. 本机 `RETRY_BACKOFF_MILLIS` 是16/20/30秒，`RETRY_DELAY_MILLIS` 为16秒。失败提示直接打印基础常量，后续轮次未必准确反映实际阶梯（第二轮实际20秒仍可能打印16秒）。本次首次出站失败对应16秒档。
3. 设定动机来自仓内旧 MIB3 4580 固件研究及断开重连经验：`mediaDisconnectTimeout=15000ms` 加1秒余量，避免密集拨号反复扰动车机移除旧设备过程。这是历史兼容策略，**不是本次 Q4 首连必须等16秒的测量证据**；也不同于 `BtSessionGate` 的手动断开冷却或 AirPlay Error=3 退避。
4. 35.391+16s≈51.391。40.615 BT SYN、45.718凭据、51.277配对成功均已发生；入站监听没有被该 sleep 阻塞。末尾摘要进一步确认成功会话是 inbound。日志没有证明本轮依赖下一次出站重试。
5. 用户描述的反复出现，与“每轮 HFP/A2DP 已在线，主动探测失败，随后车机反向连接”的模式相容；需要多次冷车对照确定，不能以一份日志断言根因或预测缩短退避收益。

**建议顺序：**先把提示区分成“主动连接失败，入站仍在等待/推进”及实际退避档；再对选定 Q4 目标做配置文件释放与首次拨号的统一仲裁，避免 `connectLoop` 与 `startAudioProfileGuard` 两处重复动作；必要时单独比较短暂优先入站窗口与现状。不能直接取消出站兜底：历史 E8 有入站迟迟不完成、出站取得凭据的反例。保留 owner/代次、目标限制、手动断开冷却及离车截止时间。

## 2. 48K PCM 完整路径与延迟位置

```mermaid
flowchart LR
  A[音乐/导航/系统声音] --> B[Car+采集与源端混音]
  B --> C[本地CarLife音频socket与读缓冲]
  C --> D[routeAudio / CarLifeAudioSink]
  D --> E[AudioIngressQueue 复制一次并异步交接]
  E --> F[AudioSender 原生48K双声道直通组帧]
  F --> G[352帧 PCM换序 / ChaCha20-Poly1305 / RTP]
  G --> H[UDP / Wi-Fi]
  H --> I[Q4接收缓冲 / 解密 / 输出 / 扬声器]
```

| 环节 | 当前实现与成本 | 本次证据/限制 |
| --- | --- | --- |

### 降低延迟：优先级与实验判据

1. **先压抖动，保持250ms基线。** 同一设备同步记录音频worker/CarLife读线程/视频线程的线程CPU时间、Runnable/Running/I/O等待、GC暂停、频率，以及queue年龄分布、在途块年龄和send分布。Android [系统跟踪类型说明](https://developer.android.com/topic/performance/tracing/profile-types-overview)与[trace检查说明](https://developer.android.com/studio/profile/inspect-traces)可用于区分调度等待和CPU执行；这是测量方法，不是本次根因证据。
2. **独立试验降低`audioLatencyMs`，例如250→200→150ms逐档。** 只是候选，不改本次默认值。只改已选定Q4 media/48K档，不连带TTS/通话；重建会话生效，测声学端到端与音画同步、开始/暂停/导航/通知恢复、30–45分钟长程及抖动场景。车机可能忽略设置或更易欠载；理论参数少50/100ms不保证实听等量减少，本次394ms长尾反而提示需要留余量。
3. **缩短源块/减少突发需源端支持。** 当前每块21.333ms，若Car+允许更小块才可能减源块形成及组帧尾等待；更多唤醒/调用会增加CPU。没有可用源端控制证据前不猜命令、不改352 SPF、不另加每7.33ms睡眠节拍（会增加唤醒和排队）。
4. **不先缩200ms队列、更不扩大缓存掩盖问题。** 队列大多数时刻不满；降低上限主要更早丢旧音频，可能牺牲连续性，不是无损减延迟。gap当前清尾并重置marker但RTP游标按实际发送前进；本轮controlPort=0，不能假设丢弃后总有重同步。任何时钟/时间戳改动都单独实验。
5. **首声就绪与稳定播放延迟分开。** 提早音频协商只可能减少建链期等待；本轮起播前没有真实PCM的时段不能用提前SETUP凭空消除，也不能当成持续音频250ms参数的验证。

### 降低手机CPU：可做但需按收益排序

| 顺序 | 候选 | 预期范围与约束 |
| --- | --- | --- |
| 1 | `AudioIngressQueue`按media/speech维护增量字节/时长计数，替代每次`filter`、`sumOf`和删除重扫 | 确定存在额外遍历/临时集合，尤其积压时；正常队列很短，预期小收益。保持超预算、过期、speech隔离、128块上限和gap语义，不用无界队列 |
| 2 | 有界PCM块池，回收消费完成/丢弃/关闭的数组，减少`copyOf`分配 | 可消除约46.875次/s、192KB/s媒体数组分配；仍需复制读缓冲，不能让异步worker借用会被下一次socket读取覆盖的数组。若进一步做所有权交接，必须重做读端/池的生命周期设计，不能直接删copy |
| 3 | 只有Android CPU profile显示加密占主要CPU后，比较平台/native与BC实现 | 当前cipher和大缓冲已复用，剩余AEAD参数及实现内部对象可测；保留唯一nonce、AAD、换序、seq/ts、独立解密等价与失效隔离。旧JDK分配探针的95%封包分配减少不能当作本次手机CPU收益，也不能保证换provider更快 |
| 4 | 让静音检查按状态/截止时间唤醒，保持及时恢复；审计日志/feedback/视频共享开销 | 当前连续播放仍每秒10次检查但不发静音；可减少唤醒，预计小收益且非音频主热点证据。必要的空闲静音PCM仍有约1.575Mbps UDP载荷，不能套用“AAC静音十几字节”的旧注释；不能直接关闭它导致首次音乐无声回归 |
| 5 | 电平抽样、细粒度同步/计时调用仅在profile证明必要时调整 | 每秒约6000次16bit抽样，低于全面读写采样；锁和计时也有成本，但目前没有CPU占比。不要为微优化先删除故障证据或抹掉并发保护 |

现有的固定尾缓冲、借用完整帧、cipher/wire/DatagramPacket复用、原生48K快速路径继续保留。当前PCM不跑`AacLcEncoder`；改AAC可能减无线带宽但引入有损编码、编码延迟和CPU成本，不能当作本次“降CPU且降延迟”的默认方案。
