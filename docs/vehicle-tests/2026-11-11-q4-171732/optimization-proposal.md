## B1/B2：统一 HFP/A2DP 释放与拨号

### 当前调用图与确认的缺口

| 入口 | 当前动作 | 竞态/成本 |
| --- | --- | --- |
| `Iap2BluetoothClient.connectLoop` | `tryConnect`失败→`BtProfiles.disconnect`→再`tryConnect` | 拨号前检查`dialAllowed`，但profile释放内部没有工作票据/BT owner复核 |
| `SessionController.startAudioProfileGuard` | 独立线程每1.5s查询并释放，直到`iap2Ready/sessionActive/isStreaming` | 已有入站owner但未ready时仍可能工作；查询后至实际断开间也存在窗口 |
| `MainActivity.onBondStateChanged` | 配对成功后立即及1.5s后各执行一次释放 | 第二次可能晚于入站建立；若只改前两处仍留下绕过路径 |
| 启动诊断线程 | `BtProfiles.connectedNames` | 与拨号/守卫争用同profile初次代理获取，不能让纯诊断重复发起高成本系统获取 |
| `BtProfiles.proxy` | 命中缓存则复用；未命中各自申请，回调后再选择胜者 | 已避免缓存泄漏，但**没有合并正在获取的请求**，多个线程可同时发起同profile获取 |
| `BtLinkOwnership` | 入站accept后claim；出站socket.connect成功后claim | 保护已建立session的归属，未覆盖“profile操作中/出站connect中”这段前置动作 |

这些是静态可达窗口，不等于本次日志已证明重复释放实际拆掉了会话。`disconnect`的返回列表是原先在线的profile，不证明每项都成功断开；应保留实际状态确认。

### B1：同profile共享一次获取

在现有profile缓存旁增加`ACQUIRING/READY/RETIRED`条目，创建条目和选定唯一申请者只用短锁；系统获取、等待、回调处理不在该锁内阻塞。其他调用者等待同一条目的结果，沿用原有约1.2秒获取预算，不把不同profile一并锁住。

- 正常缓存命中行为不变，继续复用 `ProfileProxyLease` 的迟到资源退役保护。
- 单个等待线程取消只退出自己的等待；不能销毁其他等待者正在使用的共享获取。条目自己的超时/服务断开/蓝牙退役决定何时关闭它。
- 缓存失效时比较原条目身份，旧callback不能删除新条目；系统接口返回false和迟到成功都须有收尾。
- 不在主线程等待。Android文档明确 `getProfileProxy` 的 `ServiceListener` 回调在应用主Looper执行；持锁等主线程回调会引入死锁风险。[API依据](https://developer.android.com/reference/android/bluetooth/BluetoothAdapter#getProfileProxy(android.content.Context,%20android.bluetooth.BluetoothProfile.ServiceListener,%20int))
- 初版不新增永久“不支持该profile”缓存，不并行重写各profile等待，不改变LE_AUDIO策略；它们会增加故障分类与失效条件。

### B2：一个仲裁状态，三个动作入口

建议由BT层持有会话级动作协调器，而不是各入口自行执行`disconnect`。请求携带选定目标、原始用户工作票据、动作代次和原因。它与现有 `BtLinkOwnership` 在同一仲裁边界提交状态，避免“先看owner为空、随后另一个锁登记动作”的检查/执行竞态。

概念状态：`IDLE → RELEASING_PROFILES → DIALING → SESSION`；`BACKOFF/STOPPED`按原预算进入。状态只描述当前动作，不替代既有iAP2协议状态机，也不把dial占位伪装为已建立session。

| 事件 | 建议决策 |
| --- | --- |
| 客户端与守卫同时请求释放同目标 | 合并为同一个进行中操作，重复请求附着/跳过；不分别执行完整释放、等待和兜底 |
| 同目标正在出站connect，守卫发现profile在线 | 不同时发设备级断开；先等待该拨号的完成/失败/取消，再交由同一策略决定释放 |
| 当前目标入站accept通过校验 | 若尚无已建立session，入站占用会话；作废未执行释放与出站拨号票据，关闭仅属于该拨号的未完成socket；不得关闭新入站socket |
| 任一方向已有合法session，尚未ready | 暂停新profile破坏性操作，而非等到ready才停；仍受原握手超时约束，失败后恢复原有兜底，不永久只等入站 |
| 旧拨号晚成功、旧profile等待结束 | 按原票据复核，不能提升为新session或继续二次拨号/设备级断开 |
| 停止、目标切换、工作轮次更换 | 取消当前动作及待执行动作，只关闭所属资源，不因队列中新请求延长离车预算 |
| 配对完成后第二次释放 | 使用同一协调器；当前目标已变或session存在即跳过，不能走直接`BtProfiles.disconnect`旁路 |

实施上，入站accept不能排在阻塞的`socket.connect()`后面，因此不是把所有BT I/O塞进一条串行线程。采用短锁提交动作许可，I/O在锁外运行，完成时带原token返回；每次破坏性系统调用前与1.5s/0.5s等待后复核许可。设备级disconnect兜底与下一次拨号必须能被入站/取消撤销。

**硬边界：**已经提交给Android的profile断开命令无法保证撤销，accept也不等于车机物理连接刚刚开始。方案能消除本机尚未发出的重复/过期动作，不能保证空口永无瞬时重叠。不要在仲裁锁内持有蓝牙Binder调用或close，防止回调/stop互锁。

为此建议把`BtProfiles.disconnectAddress`拆成可检查许可的“状态快照→profile级请求→状态等待→可选设备级兜底”，返回结构化结果（已提交、实际离线、已被入站取代、已取消、失败），替代仅返回名称列表。诊断只记录原因/耗时/代次/计数，身份按既有脱敏规则处理。

### B2 第一版验收与更激进顺序的边界

- 确定性并发测试：双释放合并；诊断/守卫/拨号同时获取代理；入站发生在首次dial、profile等待、兜底前、二次dial前；旧connect晚成功；旧finally；手动取消/目标切换；同一owner的会话不被旧操作关闭。
- 必须覆盖入站失败后出站仍能接续，以及CarPlay仍工作时既有“只补连当前目标控制链”的例外，避免修成永久静默。
- 车测按相同冷车条件比较HFP/A2DP在线、仅配对、车机主动连接、快速重连；分别覆盖CarLife先起与CarPlay先起。记录每类动作次数、到凭据/首帧/音频就绪时间与失败率。
- 若后续要对本Q4改成“确定profile在线就先释放、再拨号”，这是**独立顺序实验**。本次31.263–35.391的4.13s包含多种动作，不能承诺先释放就省4秒，更不能承诺省16秒。首版不新增固定入站等待窗。

## N1：有有效邀请时减少同网重复公告

### 当前机制为什么不够

`CarPlayCtrlAdvertiser.ensureForNetwork`已有2秒force冷却，已能抑制紧邻的重复调用，并且同网重播复用TCP端口。`AirPlayClient.runPairing`仍在attempt=1调用`retryTick`，控制器随后强制重播。样本49.092已收到邀请，50.149仍重播，离47.167登记超过2秒，因此冷却并不覆盖这一情况。

不能用`inviteCount>0`或`PendingCtrlInvite.recentAge!=null`直接跳过：前者没有有效期，后者主要用于邀请接续/BT交接，只保留工作代次和时间，不含网络/监听器归属，而且可因消费或活跃控制分支失效。`WifiIdentityProof`带实际本地接口但也是另一种用途，不能把“允许识别网络”变成“已成功公告”的证明。

此外，当前`registered=true`是在`registerService`返回后设置，代表已提交请求，并非收到注册成功回调。Android注册是异步操作，成功与失败由listener报告。[API依据](https://developer.android.com/reference/android/net/nsd/NsdManager)

### 建议采用窄范围、可回退的跳过策略

1. 将公告状态区分为`SUBMITTED / REGISTERED / FAILED`，带当前公告代次；旧listener回调只影响旧代次，不新增同步等待。现有“同网重复请求合并”可继续使用SUBMITTED状态，不能因此扩大重播。
2. 独立记录“用于避免重复公告”的邀请证据：目标匹配、连接工作代次、当前具体Network/绑定租约代次、实际本地接口、TCP listener身份、公告代次、接收时间、200应答写出结果。沿用30秒有效期作为初始候选，不延长、不因查询刷新。
3. 保留当前邀请回调的执行顺序及建链行为。只有应答写出后才补记可用于跳过的证据；若首次配对钩子先到，就保守保留原重播，不等待应答、不延迟配对。200写出仍不代表车机收到或AirPlay服务可用，只是本机去重判据之一。
4. **第一版只跳过首次配对钩子的同网重播**：当前目标/工作票据、网络及租约、接口、listener、公告代次全部匹配，公告REGISTERED、监听存活、邀请未过期且已写应答。一次证据最多用于一次跳过，归属当前setup，不让同一旧邀请跨失败重试反复抑制广播。
5. 换网、listener重建、TXT身份修复、注册失败、服务丢失、断线/取消、新轮次、目标切换一律清除证据。后续周期重试、端口拒绝叫醒、无邀请和未知身份路径仍走原策略；不把“同SSID”当“同Network”，也不能沿用代码里`network=null`的宽松sameNetwork判断来授权新跳过。

建议只新增带reason的重播决策，不把所有`force=true`替换成false。`retryTick`本身仍执行必要的端点/状态检查，只将其公告子动作变成`SKIP_CURRENT_INVITE`，并改清楚“首次尝试”日志。

**预期：**本样本可能避免一次92ms的本地重播调用与异步注销/注册；“可能”是因为原导出未保留这条邀请的`response-written`诊断，当前代码存在但不能补造当时成功结果。它不是秒级连接提速承诺；主要减少重复系统操作和无必要公告变化。

测试：新鲜合法邀请命中；重复邀请；消费待决邀请后去重证据仍独立；超时边界；同SSID换Network；旧listener/公告callback；200写出失败；未完成注册；服务丢失；端口拒绝恢复不被抑制；流中邀请行为不变。Android设备fixture验证实际NSD回调归属，JVM仅验证纯决策不能替代系统回调测试。

## A1/A2：音频CPU第一批只改队列内部

### A1 分类增量计数，保留队列顺序

当前`offer`每次用`queue.filter { speech相等 }`，再统计字节与时长；每淘汰一次又重算。增加media/speech各自的待处理块数、有效字节数、累计时长，在enqueue/take/drop/close四处维护，现有总量用于日志。正常offer只比较计数，超预算时才查找最早同类块并删除。

保持单个全局FIFO，不改成两条队列交替消费（会改变音源顺序）。保留media200ms/64KiB、speech10秒/512KiB、128块上限、单独合法大块接纳和gap规则；在途块仍按原实现不计待处理预算。旧算法可放在测试作为参考模型，随机混合offer/take/时间推进/drop/close，对比输出顺序、gap、丢弃及预算。

这个改动消除可确认的冗余分配/扫描，风险较低。但正常队列通常0–1块，不能预计显著整机CPU下降；优先价值是减小热路径工作量且行为容易证明等价。

### A2 首版采用单一4096B媒体块池，不做复杂零拷贝

常见输入为4096B，每秒48000×4/4096=46.875块。当前reader已经复用缓冲，真正剩余的数组分配在`AudioIngressQueue.offer`的`copyOf(size)`。

建议每个AudioIngressQueue只管理**普通media、size恰为4096**的池；其他大小、speech继续分配精确大小数组。候选上限为16个槽、64KiB数组内容，懒分配；该上限包含空闲、排队、在途的池槽，不是额外扩大的音频队列。200ms内通常最多9个4KiB待处理块，再加1个在途；16槽有余量但仍应测量命中率。

- 借用槽→复制有效4096B→排队→消费返回→归还。队列预算/统计仍按有效字节，保持现有回调数组长度语义，不把更大的池容量当作有效PCM发送。
- 过期/溢出drop立即归还；close只回收尚未消费的块并释放空闲引用，**在途块必须等consume的finally才释放**。close/异常/重复close都不得双还、跨新队列还或覆盖仍在发送的数据。
- 空池且未达槽上限才建槽；达到上限采用原有精确数组分配兜底、消费后丢弃，不能阻塞socket读线程等待归还，也不能为了池命中额外丢音频。非池fallback数组不偷偷纳入16槽预算之外的缓存。
- 继续在现有短队列锁内维护槽和复制，避免新全局锁/新线程；不同时把复制搬到锁外引入预留/取消事务。
- 消费端只允许在回调期间借用数组。现有测试如果在回调后保留数组引用，应在测试回调内复制再断言；不能让测试偶然未被覆盖掩盖所有权问题。

池化只能减少数组**分配**，不能减少这192KB/s跨线程**复制**；Block/Delivery和其他对象仍可能分配。按标准速率，30秒约避免1406个4KiB数组；实际以poolHit/miss、分配采样为准。第一版不池化元数据对象，不把可变对象跨线程复用，不改读线程/UDP线程为同一线程。

对象池也可能因同步和保留更多活对象而更慢，Android官方明确要求评估，而不是把“少分配”当作“CPU必降”。[内存管理依据](https://developer.android.com/topic/performance/memory/manage-app-memory#memory-churn)

验收：原数组立即覆盖仍输出一致；两种音源交错；9块媒体预算边界；异常长度/大TTS；池耗尽不阻塞；停止时消费被阻塞；drop/close/consume只归还一次；新旧sender隔离；解密后的PCM逐样本相等、352 SPF/seq/ts/nonce/marker保持。

## A3/A4：第二阶段再评估的CPU工作

### 静音线程唤醒

目前持续PCM每约21ms到达，静音线程仍每100ms醒来检查；正常播放无静音包，唤醒仍存在。建议以`lastRealFeedAt + threshold`为下一次资格检查时间，醒来读最新输入时间重算，而不是每次PCM都cancel/reschedule定时任务。这样稳定播放约每300ms检查一次，而不是每个PCM触发新唤醒。

STOP将门槛降到50ms时必须通知等待者提前醒；进入补静音状态仍保留100ms节拍、每拍最多16帧、pending/inFlight优先与每包再检查真实输入。START/真实PCM恢复和stop也要有防丢通知的状态/代次；虚假唤醒重查条件。补帧资格受lastRealFeedAt影响，不能因早到STOP忽略刚收到的PCM。停止立即打断，不等deadline。

预期连续播放检查减少约60%–67%，指**该线程的检查次数**，不是手机CPU/耗电下降比例。空闲时仍须持续发静音PCM，不能关闭或降低音频包率。本修改会触及静音开始时机，因此单独车测：长期空闲后第一段音乐、通知STOP/START、无START的PCM恢复、导航TTS与媒体交错。首版不将静音职责合并到可能阻塞的发送worker，不改音频同步与feedback周期。

### 加密、日志与电平

- `PcmPacketSealer`已复用cipher/nonce/wire/DatagramPacket。只有真机线程CPU采样显示它占主要预算，才比较BC、可用平台实现或native。先做相同1408B载荷/136.36包每秒的微基准及独立解密等价，再做完整音视频并行A/B；CPU、分配、温度、发送p99一起看。不以JDK探针推算ART收益，不复用密文/nonce、不删除认证、不为省调用改大包长。
- `AudioContinuityWindow`约136次/s更新、输入约47次/s；电平约6000次采样/s，当前都不能据此断言是热点。只有profile支持时再调整采样率/计时调用或单独归并计数，保留异常证据和并发安全。
- 本样本controlPort=0，不存在可裁掉的音频RTP同步线程；其他timing/feedback有协议用途，不纳入无证据减频。
- 音频优化保持48K/16bit/双声道、无损样本、队列及协商延迟不变；不采用AAC或改视频配置来包装成“音频CPU优化”。
