## 优化建议与风险（没有实施连接修改）

1. **优先收敛重复入网任务及过期兜底，避免成功后假失败。** `onWifiCredentials` 会预先入网，正式连接又接续同一次入网请求。19:05:27.675 日志进入名为“用户选择手动连接”的路径，19:07:31.758 才超时（约 124.083s），而媒体持续正常。源码该日志来自 UI 分支，但仅凭导出不能核验点击者或具体来源，不能否定用户“无额外干预”的描述；可以确认它发生在首帧之后，不是建链成功的前提。应由同一代次统一消费入网结果；连接成功后取消旧提示/轮询，写界面状态前核对代次、网络与会话状态。该遗留等待不增加首次出画面时间，却会污染 UI 状态及下一轮处理。
2. **当前代次的车机邀请/已连网络可成为快速成功条件。** NetworkSpecifier 回 Unavailable 不等于系统 Wi-Fi 没连上。13.442–22.556 有 9.114s 可疑等待，其中邀请后仍等待 3.918s 最有明确证据。建议在等专属网络时并行观察现有 Wi-Fi，以网络路由、已知车机身份和当前邀请交叉确认；满足条件后结束多余等待，保留原失败回退。不能只绑定任意 Wi-Fi，SSID 读不到也不能直接判定未连接。不同 ROM 必须单独验证。
3. **区分认证长度拒绝与传输断开，防止错误记忆导致额外探测。** `Iap2SenderSession` 当前把挑战期间 socket 关闭直接记为长度硬拒绝。第一轮因此拒绝 20B，第二轮先花约 6.9s 绕行 32/16B，最后程序又记录同车 20B 成功。这不支持仅凭 socket 关闭断言长度不兼容。建议明确协议拒绝、静默、传输中断分级；传输失败保留成功记忆，必要时限次重试。最终 20B 成功已记忆，下轮可能自行避免探测，因此单样本不能保证每轮均节省 6.9 秒。此处与网络等待相关，不应机械相加宣称固定收益。
4. **保留主屏接管所需的控制就绪与补 RECORD。** “等首帧 2.3s”主要是必要的控制认证门控；直接删掉可能重现此前黑屏。可先评估更早启动控制识别、让可并行准备提前，不能跳过配对/MFi 或关键激活步骤。认证等待、音频 SETUP 和 mDNS 解析不是同一瓶颈。
5. **后续再评估缓存起播后的强制重建和辅助广播。** 以缓存 GOP 新鲜度、SPS/PPS 与当前源代次为条件，优先用已有完整关键帧；失败才重建。mDNS 重注册只在网络/接口变化时需要，须核验车机兼容性，不应因为日志有两次注册就认定无意义。
6. **修正观测口径与误报。** 起点应覆盖启动、首次 BT、失败重试、热点、配对、控制认证、首帧及首音频，而不仅从热点阶段计时；39.8s 早期阶段被旧小结遗漏。19:05:39 的“屏幕有回落信号”来自 hidSendReport/iAPSendMessage 计数，稳定投屏下普通 HID/控制流也能触发，应只作为观测，不直接判失败。日志写“15s 超时”同时包含系统提前 onUnavailable，实际等待应以起止时刻为准。
