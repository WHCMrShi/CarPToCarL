# Q4 歌曲播放进度修复（2026-11-06）

## 对 bcef70f 文档方案的评估

[原始分析](vehicle-tests/2026-11-05-q4/README.md#1-音乐进度和播放状态)的方向可行，但仅替换 title/artist 去重键不足以修复：

- SessionController 的全局去重确实拦截同曲进度、暂停/恢复和 seek。
- MediaSessionsState.publish 仅向原监听者通知曲目/播放状态/封面变化，纯位置变化被过滤；需要独立的协议采样通知，保留 UI 的既有通知频率。
- position 是播放器上次状态更新时刻的位置，不能在每次读取时把锚点重设为现在。Android 的 [PlaybackState.getLastPositionUpdateTime](https://developer.android.com/reference/android/media/session/PlaybackState#getLastPositionUpdateTime()) 与 elapsedRealtime 使用同一时钟。
- Q4 日志确认车机发送 0x5000 订阅，并在能力清单声明 0x5002 退订。周期更新须遵守订阅生命周期；同曲重订阅与新链路不能复用全局已发送键。

## 实施范围

复用 MediaListenerService 已有的 1 秒轮询与即时媒体回调，不增加线程/定时器。独立协议监听者接收每次采样，UI 监听者仍只接收内容变化。保留播放器的时间锚点，以速度外推位置；未知位置、无时间锚点、未来时间戳和非法速度不虚构进度，结果限制在歌曲时长内。

Wi-Fi 和蓝牙链路各自维护订阅及完整载荷去重，位置、播放状态、时长等变化可以发送；重复暂停采样不发包。Q4/蓝牙的 0x5002 停止更新及旧订阅重试，重新订阅强制重推当前曲目。发送提交失败不记入去重缓存。旧 type-130 隧道保留识别后可主动补推的兼容行为；没有改写其原有订阅握手。

媒体轮询只访问已有 AirPlay 虚拟链路，断开后不因歌曲采样创建新链路或 pacer。新实例拥有新的去重状态。原生音视频转发、数据库、版本号、CarLife 进度包解析、专辑名采集和封面传输均不在本次修改中。

## 回归范围

测试检查连续一分钟的编码位置、同曲暂停/恢复、前后 seek、元数据变化、独立链路/重订阅去重、失败重试和并发重复回调；核查播放器旧时间锚点、速度与位置边界、协议采样和 UI 通知隔离。虚拟 MIB3 与内存双工蓝牙链路分别检查实际 0x5001 播放字段、退订和重新订阅。

尚未实车验证。上车需检查同曲连续播放一分钟、暂停后进度冻结、恢复继续、前后拖动、同曲断开重连；对照实际仪表显示及 0x5001 的 elapsed/status。CarLife 原日志中的异常“媒体进度”数值不是此主路径输入，不能用它代替协议发送验证。

本机验证：528 项单元测试通过；lintDebug 为 0 Error、109 Warning、2 Information。未执行 assembleDebug 或其他 APK 打包任务。

## Code Review 后续修复

媒体回调不再直接进入链路锁或写 socket：Wi-Fi 只设置待更新标志，由已有 pacer 冲刷；蓝牙单线程调度器串行发送，执行时读取最新状态，最多保留一个待处理更新。缺少媒体信息的退避改为延迟任务，收到新媒体通知可立即处理，不会排在旧任务的 sleep 后面。调度器由通道拥有，通道关闭或保活泵退出后取消任务。

去重状态锁不再包围 IO；退订可以立刻使代次失效，迟到的旧发送完成不得恢复新订阅缓存。已经开始的写入不能撤回，但等待中的更新会失效。通道显式关闭先关 IO、再等待写侧状态锁，阻塞写不会拖住最终断开，底层流只关闭一次。

蓝牙统一解码入口按收到顺序记账 0x5000/0x5002，覆盖 MFi、HID、暂存队列和保活阶段；握手期间只记录最终订阅状态，进入保活阶段才发送，避免原样重新入队造成活锁。

后续修复验证：536 项单元测试通过；含完整 MFi/HID 唯一提前订阅/提前退订、阻塞写解除、非阻塞回调、最新状态合并、退订/退役取消和旧订阅隔离。lintDebug 通过。未打包 APK，未安装或实车验证。
