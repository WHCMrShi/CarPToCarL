# Q4 review 修复与 48k PCM 开销检查

本次仅修复上次 review 的四个问题，未修改 AudioSender、CarLifeAudioSink、加密或音频包格式，未构建 APK。

## 四项修复

- Q4 自动模式每轮优先重新尝试已声明的 48k media PCM，忽略该档旧拒绝记忆；失败后仍在本轮尝试其他候选。手动兼容模式保持原规则，不迁移或清空其他车机记录。
- 启动标记由单写线程的 SessionLogFile 独立写入，不依赖可能被淘汰的普通日志记录；轮转后也重写标记。
- 写盘异常会记录本进程日志不完整，flush 返回 false；后续写盘恢复不会掩盖已丢批次。导出通过已有的文件不可用分支使用内存日志并标注不完整。超时和中断返回失败，中断标志保留。
- 日志生成时同步捕获清屏代次；清屏取消待刷新批次，迟到的旧代次回调被拒绝。监听接口仅有 SessionController 和 MainActivity 两个调用点，没有外部 API 或存储结构变化。

## 48k PCM 检查（静态分析，尚无手机 CPU/功耗实测）

输入为 48kHz、16bit、双声道，目标也是同格式时，alignPcm 直接返回原数组（有效长度小于数组长度时仍会复制），dispatchPcm 不启动 AAC 编码。字节序转换不改变采样值。
因此当前路线能保持网关收到的 PCM 精度，但不能提升源引擎已经输出的音质，也不能据此声称整机功耗最低。
裸数据率为 48000×2×2=192000 字节/秒，即 1.536Mbps，不包含协议开销；PCM 比 AAC 更占无线带宽。

目前并非最优实现，主要可优化点按优先级如下：

1. AudioSender.feedPcm（约 537–546 行）：每取一包都两次 toByteArray 复制整个剩余缓冲，再 copyOf 生成帧，并把余量重新写入 ByteArrayOutputStream。大输入块会产生随分包数放大的复制与 GC。优先替换为固定大小组帧缓冲或环形缓冲，完整包直接按 offset/length 消费，仅保存尾部不足一包的数据。
2. sealPacket / bigEndianS16（约 957 / 123 行）：每包分配 header、AAD、换序负载、密文和最终 wire。可复用有明确单线程所有权的工作缓冲，在输出位置完成换序和封装，避免多次中间复制；保留原始数据所有权、序号、时间戳、AAD 和 nonce 语义。
3. AirPlayCrypto.chachaSeal：每包新建 ChaCha20Poly1305、参数对象和输出数组。可在独立优化中评估安全复用或平台实现，但必须证明每包唯一 nonce、并发隔离及密文一致性，不能关闭加密或复用 nonce 来节省开销。
4. PCM 当前每包 352 个采样帧，约 136.36 包/秒；负载 1408 字节，加 RTP/tag/nonce 后 UDP 载荷约 1444 字节。不要为减少调用次数直接增大包长，需考虑 MTU、分片、接收端契约和时延。
5. CarLifeAudioSink 每 16 个采样点抽样统计一次电平，开销优先级低于缓冲复制和加密对象；静音保活和同步包有已有兼容性用途，不应直接移除。

媒体原生 48k 路径无需重采样；导航/TTS 可能是 16k 单声道，仍要转换。现有所谓“线性重采样”实际上按整数源位置复制样本，并非线性插值。这需要单独评估音质，不能把音乐直通的结论推广到所有声音。

后续无损性能优化应先测 PCM 持续播放时的 CPU、分配率、GC、发送间隔和音频线程阻塞，再用逐采样/逐包比较与长时间车测验证。优先去掉冗余复制，不降低采样率、位深、声道，不丢音频帧，不改为有损编码；本次不实施这些数据路径改动。
