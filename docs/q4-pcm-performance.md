# Q4 原生 PCM 转发性能优化

本提交单独优化音频数据路径，面向 CarLife 合并音频通道：混音由 CarLife 完成，本应用不新增混音、增益、降噪或压缩处理。不修改画布、连接流程、音频协商或 UI，不构建 APK。

## 实现

- PCM 组帧用固定 1408 字节尾部缓冲取代每包反复 toByteArray、copyOf 和剩余数据搬移。完整输入帧按 offset 借用原数组，仅不足一包的尾部被复制。回调使用原生 Int 参数接口，避免每包偏移装箱。
- 源/目标采样率一致且双声道时直接组帧，不经过 alignPcm 或复制整个有效输入。不同源格式继续使用原有转换；AAC 回退保留原路径。
- 每个发送流拥有自己的 PCM 封包工作区：复用换序缓冲、nonce、密文/RTP 报文及 ChaCha20Poly1305 对象。仍逐包使用新 nonce 重新初始化加密状态，AAD 仍为 RTP 头的 4..12 字节。参数初始化仍有少量内部对象分配，不宣称零分配。
- 同步 UDP send 完成前不复用报文，DatagramPacket 也重复使用。发送仍受 AudioSender 的同一把锁保护；停止先关闭套接字，再在同一把锁内清空组帧尾部。发送失败中止当前输入批次，不继续灌入旧数据。
- PCM 路径去掉临时 List 包装，不修改 AAC 编码格式和加密路径，不修改原来的 352 采样帧包长、SSRC=0、Marker、seq、timestamp、静音保活与同步包。

借用约束：输入只在 feed 调用期间读取；尾部会复制；输出工作区只在 sendPayload 锁内使用，不能跨包异步持有。nonce 必须非负且在同一实例中严格递增，重复或回退会被拒绝。

## 质量与验证

同格式 48kHz 双声道 16bit PCM 不重采样、不改采样值。小端转大端是可逆字节序转换，不是有损音频处理。合并通道中的音乐、导航、提示音作为同一条已混音 PCM 流保持原顺序转发。

回归测试覆盖：随机分片与有效长度、输入调用后被覆盖、完整帧借用、停止/重置尾部、连续 1000 包与旧实现逐字节等价、独立接收端解密、seq/timestamp 回绕、不同流隔离及 nonce 回退拒绝。另有实际 loopback UDP 发送测试，验证连续复用 DatagramPacket 后接收数据仍与旧实现相同。

## 本机分配探针

`scripts/PcmAllocationProbe.java` 在编译后的 JVM 类上比较旧 sealPacket 等价实现与复用实现，不需要 APK。运行依赖 JDK 17，classpath 包含 `app/build/tmp/kotlin-classes/debug`、Kotlin stdlib 与 bcprov 1.78.1：

```text
java -cp <上述三项组成的classpath> scripts/PcmAllocationProbe.java
```

使用 ThreadMXBean 读取当前线程分配量；每轮两实现各预热 4000 包，再各测 10000 包，执行三轮。固定 1408 字节 PCM；不含分包缓冲、UDP 调用或实际 Wi-Fi。最后一轮本机 Temurin 17.0.21 的结果：

| 实现 | 分配量/包 | 耗时/包 |
| --- | ---: | ---: |
| 旧封包 | 5560 B | 30.5 μs |
| 复用封包 | 280 B | 26.4 μs |

该探针的封包分配减少约 95%，不代表整机 CPU 或功耗下降 95%。微基准不是 Android/ART 或真实车机测量，也不能据此量化手机电量收益。测试运行不会安装应用或发送真实车机数据。

PCM 原始数据量仍为 192000 B/s；不通过有损编码降低带宽，不通过增大包长减少调用次数。手机上的 CPU、分配/GC、Wi-Fi 功耗和长时间车测仍需后续核验。

最终验证：441 项单元测试全部通过，无失败、错误或跳过；`:app:lintDebug`、新增文件定向格式化及 `git diff --check` 通过。没有执行 APK 打包任务。
